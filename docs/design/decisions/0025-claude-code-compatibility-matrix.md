# 25. Claude Code compatibility is a generated, structured definition

Date: 2026-06-18

## Status

Accepted. Amended 2026-09-30: not generated yet — `scripts/regenerate-compatibility.ts`
is a stub and its `compatibility.json` output is gitignored. Amended 2026-10-25: built,
with a different source of truth and a session-start check — see the amendment below.

## Context

The system is a Claude Code logger ([ADR 0010](0010-claude-code-specific-scope.md)),
so it has a hard dependency on Claude Code's hook surface, which changes across CLI
versions. We need to know, precisely and verifiably, which Claude Code versions we
support and which hooks each version exposes — and we don't want that drifting out
of date by hand.

## Decision

Track Claude Code compatibility as a **structured, formal, machine-generated
definition** (a committed `compatibility.json`, [compatibility.md](../../start/compatibility.md)),
not prose:

- It records three versions — **`latestPublic`**, **`latestCompatible`**,
  **`earliestCompatible`** — and the **complete supported-hook list for each**.
- **`latestPublic` + the per-version hook lists are auto-generated** from an
  **external source of truth** (Claude Code's published hooks docs / release
  metadata) by a dev script, runnable locally and in CI
  ([dev-automation.md](../../develop/dev-automation.md)).
- **`earliestCompatible` / `latestCompatible`** are determined by **test
  automation** (a future suite that runs the [e2e tests](../../develop/testing.md) against
  multiple CC versions), not by hand.
- The same generated data backs the **hook-drift check** (Tier 3, #13): diff the
  codebase's hook list ([hook-events.md](../../reference/hook-events.md)) against the generated truth.

## Consequences

- "Which versions / hooks do we support?" has one authoritative, regenerable
  answer — no stale hand-maintained list.
- Tier 1 ships the **structure + the `latestPublic` generator**; the
  compatibility-window automation is gated on the e2e suite (a later milestone).
- Adds an external-source-scraping dependency in CI; if the source format changes,
  the generator needs maintenance — accepted, as the alternative is silent drift.

## Amendment (2026-10-25): the SDK release is the source, and every session checks

**Source.** The external source of truth is the `@anthropic-ai/claude-agent-sdk` npm
release cut for a Claude Code version (its `package.json` names it in
`claudeCodeVersion`), not the published docs. Its `sdk.d.ts` declares `HOOK_EVENTS` and
each `<Event>HookInput` type, so the per-version event list *and* payload fields are
machine-readable, and an npm release is immutable — the same version always yields the
same spec. The docs describe only the latest release and are prose; scraping them
would be neither per-version nor reproducible.

**Shape.** Rather than one `compatibility.json` with three versions, the build ships
the spec for **one pinned version** (`packages/shared/src/claude-code-hook-spec.json`,
generated by `gen:compat`, reproducible so it sits in `gen:all`), and the CLI fetches
any other version's spec on demand (integrity-checked, cached). `earliestCompatible` /
`latestCompatible` still await the multi-version e2e suite.

**Drift check.** The hook-drift check is no longer a Tier-3 CI job: `check-hook-compat`
runs at every SessionStart (`claude --version` → spec → compare with `HOOK_TYPES`) and
adds one line to the banner, or a summary on drift. `claude-transcripts compat` runs the
same check on demand and exits non-zero on drift. Network is never on the session's
critical path — an unknown version is fetched by a detached process and reported the
next session.

**Consequence.** The dependency is on the SDK's declaration-file layout rather than the
docs' HTML. The parser refuses a file it can't read (no `HOOK_EVENTS`, no
`BaseHookInput`) instead of returning an empty spec, so a layout change surfaces as
"not checked", never as false drift.
